## 结论

**方向可行，当前草案复杂度偏高，建议收紧范围后再进入技术设计。** 这次建设包含服务端购物车、持久订单与支付接入，不能按“前端视觉优化”估算。即使精简后，交易一致性部分仍是中高复杂度，不能靠减少测试、授权校验或持久化来降低。

用户已确认的目标不变：全站遵循现有设计规范；AU 从购物到沙箱支付与订单回查完整可用；SG/US 做兼容检查；需求审核后才下一步。

建议先确定一个验收运行时、一种持久存储和一种沙箱卡支付方式；将新增筛选、优惠、旧演示车自动迁移、竞争库存与新增 Blog 详情移出首轮默认范围。付款期间是否允许继续修改购物车，是一个值得用业务约束简化的选择，见 §4。

本报告不代表需求已批准、实现已通过或环境已可用，也不擅自删减用户已经确认的全站及交易目标。

## 1. Standards — 项目规范与交易契约

未发现需求文本与 AGENTS.md Hard Rules、DESIGN.md 或现有分层方向直接冲突。下面是契约与范围问题，不能表述为已复现的运行时缺陷。

### S1 · P2：幂等键不能代替业务上的唯一有效结算

**位置：** requirements.md L171、L200。

原文要求重复提交不重复下单，并限定同一订单最多一次有效收款。但两个标签页可用不同请求键提交同一个购物车版本，分别产生两张订单，仍满足这两条文字。现有 mock cart 的请求去重也不足以直接保护 checkout。

**最小修正建议：** 补充“同一 cart revision 最多一个活跃 checkout / 可付款会话”，验收两个标签页、不同幂等键并发提交同一购物内容。用户后续有意再次购买仍应允许，不能永久按商品组合去重。

### S2 · P2：支付方法范围未限定，状态复杂度没有明确上限

**位置：** requirements.md L181、L200、L254。

只有 Stripe sandbox / 托管页方向，没有限定首轮支付方法；同时承诺未知结果、迟到成功和多次尝试处理。不同方法可能引入不同确认周期，无法据此判断需要多长的处理中状态或什么恢复机制。

**最小修正建议：** 首轮只支持一种沙箱卡支付路径，覆盖成功、额外验证、支付拒绝和取消；排除转账等其它方法及订阅。仍保留可信回调、重复/延迟处理、查询未知结果与访问授权。减少支持的方法，不删除必要的异步确认。

Stripe 官方要求不能只靠顾客返回页面完成支付后处理，同一个确认函数也可能被重复、并发调用，因此 webhook 与幂等处理是必要复杂度。[Stripe 支付后处理文档](https://docs.stripe.com/checkout/fulfillment.md?ui=full-page)

**本轴：0 项硬规则违规，2 项 P2 契约/范围问题；主要契约风险为 S1 并发结算边界。**

## 2. Spec — 用户目标与功能边界

AU 沙箱支付与订单回查、SG/US 兼容目标均被覆盖。尚未发生超范围实现；以下是草案可能导致范围扩张或验收不足的地方。

### B1 · P2：可选能力混入必须范围

**位置：** requirements.md L57、L68、L145、L259。

“必要筛选”进入必做范围，但具体筛选仍是待审建议；优惠码在条件范围中又写成“首轮做”。用户未单独确认这些扩展。

**最小修正建议：** 每项能力只保留一种明确状态：Must / Conditional / Later；验收与批准结果绑定。保留基础搜索与现有排序，新增组合筛选和优惠码建议默认 Later。

### B2 · P2：沙箱可售校验被扩展为竞争库存系统

**位置：** requirements.md L75、L207。

非目标排除了真实库存仓配，但 L207 要求并发超卖处理，并进一步引入预留和超时释放选择。库存交易并非沙箱支付成功的必然前提，会增加共享库存计数、事务、释放和支付迟到后的冲突处理。

**最小修正建议：** 首轮库存定义为受控的可售/不可售与每单数量上限，服务端校验不变。共享库存扣减、预留和释放仅在用户确认需要验证有限库存交易后加入。相应 UI 不展示真实剩余库存，也不宣称防超卖已验收。

### B3 · P2：旧演示购物车自动迁移缺少业务依据

**位置：** requirements.md L161、L261。

迁移包含旧商品映射、缺少 SKU 的规格恢复、一次性幂等、部分失败及双写防护；原始需求没有历史购物车保留诉求，也没有证据证明当前演示车存在必须迁移的数据。

**最小修正建议：** 建议首轮不自动迁移，在明确提示后使用新沙箱购物车，旧数据不被静默删除。若用户要求旧车连续性，再保留 CART-06 并为真实迁移样本设计映射。

### B4 · P2：一笔交易不足以验收“全站可购买”

**位置：** requirements.md L77、L229、L256。

草案允许未映射商品不可购买，但主要验收只有一笔成功订单。可能出现少量商品能下单、主要目录仍无法购买，却被报告为全站完成。

**最小修正建议：** 审核时冻结首轮可交易商品集合，覆盖保留的主要购物分类以及单/多规格路径。所有公开购买入口都必须属于该集合并具有有效交易映射；展示专用商品明显标识。数据和入口覆盖检查全量进行，浏览器支付使用代表场景抽样；不要求每个 SKU 都手动付款一次。

如果采用“小型沙箱商品集”，应把它作为明确的范围取舍交给用户批准；不得将仅一两个测试商品走通等同于整个电商项目完成。

**本轴：4 项 P2 边界判断；主要验收风险为 B4 可交易商品集合未冻结。**

## 3. 可行性：现有能力与落地条件

### F1：目标运行时存在具体路由差异，不能仅将 D07 当作部署地址选择

PRD L110、L215、L238 要求保留市场规范化与隔离行为。[部署脚本](../../../scripts/deploy-cf.sh) L24–26 会在构建期间移出 `src/proxy.ts`；[市场 layout](../../../src/app/[market]/layout.tsx) L5–6 又明确依赖 proxy 完成市场对齐。`planMarketPath` 同时处理裸路径与其它市场前缀，影响并不限于脚本注释中的裸路径跳转。

这是源码可见的交付差异；本轮没有运行 CF 页面来复现其用户表现。OpenNext 官方当前支持表仍列出 Node Middleware 不受支持，因此不能假设部署脚本移走 proxy 后，项目要求自然成立。[OpenNext 支持范围](https://opennext.js.org/cloudflare)

**建议的最小处理：** 只选一个主要验收运行时。若选已有 standalone 路径，保留它作为主交付环境；若选已有 Cloudflare 路径，先证明 `/products/...`、`/{otherMarket}/...` 的规范化和价格/会话市场一致性，并验证 webhook POST 不被市场跳转破坏。修正等价行为，不重开框架选型，也不降低市场规则。

### F2：持久存储是必需能力，但不需要通用存储框架

当前 [mock cart](../../../src/adapters/commerce/mock/cart.ts) L30–34 把购物车、幂等记录和并发队列放进内存 Map；[Wrangler 配置](../../../wrangler.jsonc) 没有交易数据库绑定。配置未出现绑定不代表账号没有数据库，本轮没有检查远端资源。

“重启后仍可查单”要求选择一个持久数据源并具备必要的原子写入/唯一性约束。若使用 Workers，不能用本地 JSON 文件或 `/tmp` 冒充持久存储；官方文档说明 `/tmp` 是单请求临时文件。[Cloudflare 文件系统文档](https://developers.cloudflare.com/workers/runtime-apis/nodejs/fs/)

**建议的最小处理：** 一个运行时 + 一个持久存储 + 一个支付 adapter；复用项目 ports/adapters，不新增可热插拔数据库框架，不为两个尚未使用的存储后端写抽象。状态需要持久化不等于每一种状态都必须拆成独立服务或独立数据表。

### F3：先证明外部条件，再估算完整交付

需求批准后的首个验证任务应证明：可用沙箱账号、测试支付会话创建、回调验签、数据库写入/唯一约束、运行实例重启后查单，以及目标运行时路由正确。OpenNext 提供 Stripe 接入说明，说明存在接入路径；它不证明本项目已兼容或已完成接入。[OpenNext Stripe 指南](https://opennext.js.org/cloudflare/howtos/stripeAPI)

这一步不要求先建设部署平台、监控平台或通用后台。当前未检查账号权限、数据库资源或已部署服务，因此不承诺工期与现成可用环境。

## 5. 建议冻结的最小功能边界

| 范围 | 首轮建议 | 验收边界 |
| --- | --- | --- |
| 全站视觉与导航 | Must | 所有现有公开页面符合 happy-dog；保留入口有效；空态/错误态/键盘/移动端可用 |
| 商品浏览 | Must | 现有分类/排序 + 基础搜索；全量购买入口映射检查；至少覆盖单规格、多规格、不可售、数量上限 |
| 购物车 | Must | 持久化、匿名凭证、变体分行、数量操作、市场隔离；同车唯一有效 checkout |
| 结算 | Must | 单页游客表单，一种批准的沙箱配送规则与一种明确税费口径；精度、币种、服务端校价与变更确认 |
| 支付 | Must | 一种托管沙箱卡支付；可信回调、拒绝/额外验证/取消/未知状态恢复、持久幂等 |
| 订单 | Must | 持久订单详情、同浏览器授权回查、可重新找到订单的入口；不能只是瞬时成功页面 |
| 订单列表、Blog 详情 | Conditional | 只有明确入口或内容需求时加入；若不做订单列表，至少保留“查看最近订单”入口，明确有效凭证和保留期 |
| 新筛选、优惠码、旧车自动迁移、竞争库存 | Later | 不影响沙箱主购物闭环；未来有明确业务场景再引入 |
| 会员、收藏、比较、跨设备恢复、邮件平台、真实后台 | Later | 与原始非目标一致；不展示未实现功能为可用 |
| 市场与环境 | Must | AU 完整支付；SG/US 路由/币种/cart 隔离；只选一个主要验收运行时，不同时建设两套交付栈 |

上述 Must 是本次评审推荐基线，仍需用户审核，不覆盖原稿中尚未冻结的 D01–D08。

## 6. 复杂度评估

“低/中/高”表示状态分支、外部依赖和验证面带来的相对工作量，不代表工期承诺。

| 工作域 | 原草案 | 按建议精简后 | 原因 |
| --- | --- | --- | --- |
| 设计统一、全局壳、基础搜索 | 中 | 中 | 页面数量与移动/错误状态仍需逐一处理，已有组件可复用 |
| 变体与商品交易映射 | 中高 | 中 | 按批准集合映射；公开购买入口仍要全量覆盖 |
| 服务端购物车 | 中高 | 中高 | 持久化、会话、并发首次加购、授权不能省；可去掉迁移与付款中合并 |
| 配送、优惠、税费 | 高且边界未定 | 中 | 一种配送、一个税费口径、无优惠引擎；不同时建设含税/未税切换系统 |
| 支付与订单 | 高 | 中高 | 限定一种支付方法和一个有效会话；可信确认、失败恢复和持久订单仍必要 |
| 共享库存 | 高 | 低 | 首轮仅测试可售/缺货与数量上限；不声称验证库存交易 |
| 目标运行时与存储 | 未确定 | 待最小验证后评估 | 不能靠文档选择消除当前 proxy 与持久化差异 |

没有依据给出“工作量降低 X%”或精确天数。最值得删减的是未确认的业务分支与外部系统数量，不是文档行数、测试数量或项目治理。
